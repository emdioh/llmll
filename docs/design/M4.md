# M4 — Candidate queue and budget, contests, initial assessment

Design spec for milestone M4 (see `ARCHITECTURE.md` §13). Builds on M1–M3.
References: `R§n` requirements, `A§n` architecture. Deviations go at the end of this file.

**Usable result:** the full requirements loop: new words and grammar flow in under a weekly budget
the learner controls, gradings can be contested and reverted cleanly, and a short placement test
seeds the learner model.

## 1. Candidate queue and weekly budget (R§7.4)
Most mechanics exist since M1/M2; M4 completes and exposes them.
- Pure `candidate_queue(learner_items, items, now) -> list[item_id]` in `app/domain/budget.py`:
  order by source (`optin > article > wordlist`), then prerequisite readiness (all `requires` are
  `introduced`/`presumed_known`; not-ready items are skipped), then level, then curriculum order
  (grammar) or `frequency_zipf` desc (lemmas), then id.
- Grammar points follow the same queue with the separate weekly limit.
- Backlog definition (shared by budget and session builder): number of memories with
  `due ≤ now`. Budget reduction per M1 §3.6.
- `GET /api/queue` → `{budget: {lemmas_left, grammar_left, backlog}, next: [{item_id, label, source}]}`
  (first 20). `POST /api/items/{id}/optin` and `POST /api/items/{id}/optout`
  (`optout` sets status `suspended` for unseen/candidate items; reversible via `optin`).
- Settings UI: weekly limits, review cap, production slots, retention; queue preview on the Session
  view ("This week: 12/20 new words, 1/2 grammar points").

## 2. Contests (R§8, A§6.4)
- `contests` table (migration `0005`): `id`, `evaluation_id`, `item_ids` JSON (contested items;
  empty = whole evaluation), `reason` text null, `status` (`open|resolved`), `verdict`
  (`accepted|rejected|partial`) null, `resolver` str, `rationale` text, `replacement_evaluation_id`
  null, `created_at`, `resolved_at`.
- `ContestResolver` Protocol and `Resolution` dataclass exactly as in A§6.4; `AcceptAllResolver`
  in `app/services/contests.py`; resolver chosen by setting `contest_resolver` (default `accept_all`),
  via a small registry so future resolvers (stronger-model re-grade, native review queue) plug in.
- Application (one transaction):
  1. create the replacement `evaluation` with `supersedes = <old id>`: contested errors removed,
     contested items become `correct` (confidence 1.0) — or as the resolution's replacement says;
  2. set `voided_by = <replacement id>` on all events with `evaluation_id = <old id>`;
  3. emit the replacement's events with their **original timestamps** (the answer happened then);
  4. `replay` every affected (item, facet) from its non-voided events;
  5. remove/restore remediation-queue entries created by the old evaluation accordingly.
- Flashcard attempts (no LLM evaluation) can be contested too: M4 adds a synthetic `evaluations`
  row for flashcard attempts (grader `flashcards.v1`) so all contests go through the same path.
- API: `POST /api/evaluations/{id}/contest {item_ids?, reason?}` → resolution + updated item outcomes.
  `GET /api/contests` (list, for review).
- Frontend: enable "Secondo me era giusto" on feedback views (whole answer, or per item via the item
  list), show the result inline ("Ok, conteggiato come corretto").

## 3. Initial assessment (R§6, A§6.5)
- Shown after learner setup (skippable, re-runnable from Settings). Duration target: ≤ 5 minutes.
- **Vocabulary part:** 30 recognition items sampled by a pure function
  `sample_placement_lemmas(items, declared_level, seed)`: 10 per level band (declared level − 1,
  declared level, declared level + 1), within each band stratified by `frequency_zipf` terciles.
  Card format: German word → "Lo so / Non lo so", then for "Lo so" a 4-option translation check
  (self-report is never trusted alone).
- **Grammar part:** 4 guided-production exercises (M2 generator) on key points around the declared
  level, always including the word-order stages up to the declared level (inversion V2 at A2,
  verb-final subordinate at B1).
- **Effects:** every answer is a normal event (kinds `review`, weight per exercise type) tagged
  `context = "placement"` (new `learning_events.context` column, migration `0005`). Then a pure
  `estimate_level(results, declared_level) -> level` updates `learner.level` if the evidence clearly
  disagrees (≥ 70% correct one band above → raise; < 40% correct at the declared band → lower), and
  statuses are re-applied for items without events (M1 §4.1).
- API: `POST /api/placement` → `{placement_id, cards}`; answers go through the normal answers endpoint
  with the placement id as session id; `POST /api/placement/{id}/finish` → `{estimated_level, changed}`.

## 4. Tests (must exist)
- `candidate_queue` ordering and prerequisite readiness; opt-in/opt-out.
- Contest: accept-all on a production evaluation and on a flashcard attempt → events voided,
  replacement events with original timestamps, projection equals a from-scratch replay, remediation
  entry removed; contesting a superseded evaluation → 409.
- Resolver registry: a test resolver returning `rejected` leaves state unchanged and records the
  contest.
- Placement sampling (bands, terciles, determinism by seed) and `estimate_level` thresholds.
- API end to end: setup → placement → finish → level/status effects.

## Deviations
_(record any deviation from this spec here, with the reason)_

Backend implementation:

**Queue and budget**
- `candidate_queue(learner_items, items, now, *, max_level=None)` takes `LearnerItemView`/`QueueItem`
  dataclasses (domain-only types) and returns item ids; `queue_source(...)` gives the source of an
  entry. `now` is accepted for symmetry but does not influence the order. Candidates are items with
  status `candidate` (source = `candidate_source`); grammar points and constructions that are
  `unseen`, at or below `max_level` (the learner level) and ready also count as implicit
  `wordlist` candidates (this is what M2 computed at planning time; `_eligible_new_grammar` is gone).
  Within a level grammar-like items sort before lemmas. "Curriculum order" is the rank by
  `(level, grammar before constructions, id)`; the curriculum has no explicit order field.
- **Prerequisites now also apply to lemmas** (M1/M2 ignored `requires` for lemma candidates).
- **Backlog** is the number of `item_memory` rows (item, facet) with `due <= now` over all item kinds
  (M1/M2 counted due lemma items once per item). The session builder uses the same function
  (`services/queue.py::backlog`). The weekly count of introduced grammar now includes constructions
  (as M2's deviations already stated; M2's code only counted `kind = grammar`).
- `GET /api/queue` entries carry an extra `kind` field. Opt-in on an `introduced`/`presumed_known`
  item changes nothing; opt-out on those is 409. Opt-in on a `suspended` item makes it an `optin`
  candidate. The `contest_resolver` and the settings UI items of §1 need no new settings fields:
  the resolver is an app setting (`LLMLL_CONTEST_RESOLVER`), not a learner setting.

**Contests**
- Migration `0005` also creates the `placements` table (`id`, `learner_id`, `declared_level`,
  `created_at`, `finished_at`, `estimated_level`, `changed`, `result` JSON): it makes `finish`
  idempotent-safe (409 on the second call) and records what was estimated. `contests.rationale` is
  `NOT NULL DEFAULT ''`.
- Resolver registry: `RESOLVERS`/`register_resolver`/`build_resolver` in `services/contests.py`;
  `Settings.contest_resolver` (default `accept_all`); `create_app(contest_resolver=...)` injects an
  instance (`app.state.contest_resolver`); an unknown name fails at startup. `ContestResolver` has a
  `name` attribute (stored in `contests.resolver`) and receives the `Contest` row plus the domain
  `Evaluation` rebuilt from the stored result. `Resolution.replacement` is that domain `Evaluation`.
  A `rejected` verdict records the contest (status `resolved`) and changes nothing; `accepted` and
  `partial` need a replacement (500 otherwise). The contest row is created in the same transaction
  as the application, so a refused contest (404/409/422) leaves no trace.
- **Application.** All events of the evaluation (`evaluation_id = old`, or for flashcards recorded
  before M4 with no `evaluation_id`: the events of the same `attempt_id`) are voided, **including
  unchanged ones** (`introduce`, `status_change`, items outside the contest), and each is re-emitted
  at its original `ts` under the replacement evaluation with only outcome, confidence and tags
  replaced for items in the replacement. Replacement events get new ids, in the original order, so
  replay order `(ts, id)` is deterministic; a copy can therefore sort after other events of the same
  item that share its timestamp or were recorded later with an equal `ts`. Items without an event in
  the original evaluation (no evidence) get none in the replacement. Affected `(item, facet)` pairs
  are rebuilt with `replay_key` once, after all writes (`store/events.py::replace_events`).
- **Remediation.** Only unconsumed rows with `evaluation_id = old` are touched: deleted when the
  item is no longer an `error` in the replacement, else re-pointed at the replacement. Rows already
  consumed (their exercise was planned) stay, and a row refreshed by a later failure carries that
  later failure's evaluation id and is therefore not touched. A row that merged tags of earlier
  failures is deleted as a whole.
- Contesting never reverts a learner status (`introduced` stays), only the events.
- The replacement evaluation keeps `lt_matches`, has `grader_version = "<old>|contest.<resolver>"`,
  `llm_call_id` null and, when it is all correct, `corrected_sentence` = the learner's answer text
  (when there is one) and the feedback "Ok, conteggiato come corretto.".
- **Flashcards.** New flashcard answers (recognition and production) create the synthetic
  evaluation (grader `flashcards.v1`, `result` in the usual shape, no errors) and their events carry
  its id; `AnswerOut.evaluation_id` exposes it (null for intro cards, which are not contestable).
  Attempts recorded before M4 have none: no backfill migration; the new endpoint
  `POST /api/attempts/{attempt_id}/contest` creates the synthetic evaluation from the attempt on
  demand (outcome from `attempts.outcome`, tags from its events) and then contests it. The events of
  such attempts keep `evaluation_id` null (the log is append-only) and are found through `attempt_id`.
- API additions: `ContestOut`/`ContestResultOut` (`contest`, `evaluation_id` = the evaluation that is
  current afterwards, `items[{item_id, label, previous, outcome}]`); `item_ids` not in the evaluation
  are 422; `GET /api/contests?limit=` lists newest first.

**Placement**
- `learning_events.context` is copied by contests and set from the exercise: `session_id` starting
  with `placement-` (the placement id) means `placement`.
- Vocabulary cards are ordinary `flashcard_recognition` exercises. "Non lo so" is submitted as an
  answer with no `choice` (an error), "Lo so" followed by a wrong option is an error too. The grammar
  part is 4 pending `guided` production exercises (one primary target each, weight 1.0), generated by
  `prepare` and graded through the normal answers endpoint; if generation fails the card stays
  `failed` and is simply not counted.
- **Sampling.** `sample_placement_lemmas(items, declared_level, seed, cfg)`: 10 per band for
  declared-1/declared/declared+1. The curriculum stops at B1 lemmas, so a band with too few lemmas
  (or one outside the curriculum, e.g. B2 for a B1 learner) hands its share to the other bands, the
  declared band first; the result is ordered easiest band first, then by frequency. Lemmas of
  user-created items are excluded. Terciles are taken in rotation (4/3/3). The seed is the placement id.
- **Grammar selection.** `select_placement_grammar`: the word-order stages are listed in
  `PlacementConfig.word_order_stages` as `(item id, level from which it is tested)`, because the
  curriculum has no tag for them: svo A1, adverb-fronting A1, verbal-bracket A1, inversion-v2 A2,
  verb-final-subordinate B1 (the YAML level of the last one is A2; the spec's "B1" is used for the
  placement). At most `grammar_count - 2` stages are used (the latest ones up to the declared level),
  so at least two slots go to other points at the declared level and one above, alternating.
- **`estimate_level`** takes `PlacementResult(level, outcome)` (level of the tested item; assisted
  counts 0.5), needs at least 4 results in a band, raises by one when the band above has >= 70% and
  lowers by one when the declared band has < 40% (raise wins). Vocabulary and grammar results of a
  band are pooled. It cannot raise a B1 learner (no B2 items) and never goes below A1.
- Items first met in the placement keep `introduced_at` null, so the assessment does not use up the
  weekly budget of new items. A wrong placement answer is a normal error (remediation entry, `Again`).
- `POST /api/placement/{id}/finish` returns `{placement_id, estimated_level, previous_level, changed,
  answered, bands}`; the level change goes through `update_learner`, which re-applies statuses to
  items without events only. A second call is 409. Unanswered cards are ignored.

**Misc**
- OpenAPI was not exported into `frontend/` (the architect regenerates it at integration).
