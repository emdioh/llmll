# M5 — Measuring quality: grader evaluation, retention, FSRS optimisation

Design spec for milestone M5 (see `ARCHITECTURE.md` §13, `REQUIREMENTS.md` §12).
Deviations go at the end of this file.

**Usable result:** the grader can be measured against an annotated dataset on every prompt or model
change, the app reports how well the scheduler is doing, and FSRS parameters can be fitted to the
learner's own history.

## 1. Grader evaluation dataset
- Location: `backend/evals/grader/cases/*.yaml` (committed). One case per file or a list per file:
  `id`, `exercise` (type, instructions, prompt, reference_solutions, targets with item ids),
  `answer`, `expected`: `overall`, `errors` (list of `{item_id|null, diagnostic_tags, severity,
  span_text}` — spans matched by text, not offsets), `correct_uses` (item ids), `notes`.
- Seed set: ≥ 60 cases written by hand (LLM-drafted, then reviewed): correct answers with variants
  different from the reference (must not be flagged), typical Italian-speaker errors (gender, case
  after prepositions, adjective endings, V2, verb-final, haben/sein, separable verbs), stylistic
  alternatives, off-task answers, multiple errors in one sentence.
- Contests feed the dataset: `python -m app.cli export-contests <dir>` writes each resolved contest as
  a draft case (expected = the replacement evaluation) for human review before committing.

## 2. Evaluation script
`python -m app.cli eval-grader [--cases DIR] [--task-config JSON] [--repeat N] [--out report.json]`:
- runs the real grading pipeline (LLM + reconciliation; LanguageTool if reachable, else recorded
  matches from the case file when present) on every case;
- metrics: overall-label accuracy; error detection precision/recall/F1 (an error matches when the
  item id — or null-null — matches and the expected `span_text` overlaps the predicted span);
  false-positive rate on correct answers (the key trust metric, R§8); item-attribution accuracy;
  tag accuracy; per-case latency and token cost; with `--repeat N`, agreement across runs
  (consistency);
- writes a JSON report and prints a summary table; exit code non-zero if the false-positive rate on
  correct answers exceeds a threshold given by `--max-fp` (default 0.05).
- Not part of CI (it costs money and needs an API key); documented in `backend/evals/README.md`.
  A unit test runs the script end to end with the fake LLM on 3 cases.

## 3. Scheduler health
- Pure `retention_report(events, memories, cfg)`: for reviews whose card had a predicted
  retrievability, bucket predictions (0.0–1.0 in 0.1 steps) and compare with observed recall
  (outcome `correct` = recalled; `assisted` counted separately); overall observed vs target retention.
- `GET /api/stats` → `{reviews_7d, reviews_30d, sessions_7d, readings_7d, new_items_7d,
  observed_retention, target_retention, calibration: [...], backlog}`.
- Frontend: a small "Stats" section in Settings (numbers + a simple calibration table; no chart
  library in v1).
- To make calibration possible, `learning_events` gets `predicted_retrievability` (float null,
  migration `0006`), filled when an event is recorded for an item that already had a card.

## 4. FSRS parameter optimisation
- py-fsrs provides an optimizer behind the `fsrs[optimizer]` extra, which pulls in PyTorch. That is
  far too heavy for the runtime image, so it is an **optional dependency group** (`uv sync --group
  optimizer`) used only by `python -m app.cli optimize-fsrs`.
- The command builds review logs from non-voided `review`/`implicit` events (per item+facet card),
  refuses to run with fewer than `--min-reviews` (default 1000), fits parameters, prints old vs new
  log-loss, and with `--apply` stores them in learner settings (`fsrs_parameters`). Changing them
  changes `ProjectionConfig.version` → full replay (`python -m app.cli replay`, run automatically by
  `--apply`).

## 5. Tests (must exist)
- Case loader and metric computation (precision/recall, span-text matching, FP rate) on synthetic
  predictions.
- `eval-grader` end to end with the fake LLM.
- `retention_report` bucketing.
- `optimize-fsrs` refuses below the minimum (optimizer itself not exercised in CI).

## Deviations
_Backend (M5), recorded by the implementing agent._

**Grader cases and evaluation**
- Case files carry three fields the spec did not list: `category` (one of `correct_reference`,
  `correct_variant`, `stylistic`, `italian_error`, `multi_error`, `off_task`; needed for the
  per-category report), `level` (learner level handed to the grader, default A2) and `draft`
  (contest exports are skipped until a human removes it). Optional `lt_matches` holds recorded
  LanguageTool matches. Unknown fields are rejected. Diagnostic tags may only be expected on
  target items, because the app offers tags for targets only.
- The seed set has 70 cases: 5 `correct_reference`, 22 `correct_variant`, 8 `stylistic`,
  23 `italian_error`, 7 `multi_error`, 5 `off_task` (35 correct answers feed the false-positive
  rate). `tests/test_grader_eval.py` validates every item id and tag against the real curriculum.
- No database session is needed: `app/evals/runner.py` builds transient `Item` objects from the
  curriculum YAML, records LLM calls in memory (`MemoryRecorder`, via the new
  `build_llm_client_with_recorder`) and calls `reconcile_answer`, extracted from
  `submit_production_answer` so the app and the evaluation share the reconciliation call.
  Every curriculum item counts as "known" for reconcile (implicit uses are not filtered).
- `eval-grader` additions: `--curriculum` (default `../curriculum/de`), `--no-languagetool` (use
  recorded matches only; LanguageTool is otherwise probed once and, if unreachable, recorded matches
  are used), `--task-config` takes inline JSON or a file path. Exit code 2 when some LLM calls
  failed (metrics incomplete), 1 for a false-positive rate above `--max-fp` or invalid cases.
  "Token cost" is reported as tokens (input/output/cache), not money (no price table in the repo).
- Metric definitions the spec left open (see `app/domain/grader_eval.py`): the false-positive rate
  counts a correct answer as flagged when the prediction has any error or an overall other than
  `correct`; tag accuracy requires the expected tags to be a subset of the predicted ones; the
  overall label is that of the reconciled evaluation; consistency is pairwise agreement.
- `export-contests <dir>`: only resolved contests on production exercises (flashcards have no
  grader); expected = replacement evaluation, or the original one for rejected contests; files are
  `contest-<id>.yaml`, written as drafts and never overwritten.

**Scheduler health**
- `retention_report(events, memories, cfg, now=None)` takes an extra optional `now` (for the due
  backlog). Only `review` events with a prediction count; `correct` = recalled, `assisted` is
  reported separately and is not counted as recalled, `error` = lapse. Calibration lists the
  non-empty 0.1 buckets only.
- `predicted_retrievability` is filled centrally in `append_event_with_decision` for
  `review`/`implicit`/`lookup` events appended after the card's last event (not for backdated events
  that trigger a replay) and is copied to the replacement events of a contest.
- `GET /api/stats`: `backlog` is the number of due memories (same as `GET /api/queue`); `sessions_7d`
  counts distinct exercise sessions with an answer in the window, placements excluded; `readings_7d`
  counts reading sessions finished in the window; `reviews_*` are non-voided `review` events outside
  the placement. Calibration items are `{bucket_low, bucket_high, n, predicted, observed, recalled,
  assisted, forgotten}`. The OpenAPI schema was not exported (the architect regenerates it).

**FSRS optimisation**
- Fitted parameters need a place to live: `LearnerSettings.fsrs_parameters` (list or null, not
  exposed by the settings API) and `ProjectionConfig.fsrs_parameters` (part of the version hash).
  The scheduler, `select_due` and the production planner take them into account.
- The `optimizer` group (`fsrs[optimizer]`) is declared in `pyproject.toml` and `uv lock` resolved it
  (torch, pandas, nvidia wheels...), so `uv.lock` grew by about 450 lines and its environment
  markers changed, but `uv sync --frozen` without the group does not install any of it. The group was
  not installed here, so the command was never run against the real optimizer: the tests use a stub.
- `--apply` refuses to store parameters whose log-loss is not lower than the current one (exit 1).
  Old/new loss use the optimizer's private `_compute_batch_loss`, the only way to score a given
  parameter set in py-fsrs 6.3.2.
- The minimum-reviews check runs before the optimizer import, so it works without PyTorch.
