# M2 — LLM layer, production exercises, grading, explanations

Design spec for milestone M2 (see `ARCHITECTURE.md` §13). Builds on M1 (`docs/design/M1.md`).
References: `R§n` requirements, `A§n` architecture. Deviations go at the end of this file.

**Usable result:** a complete review session: flashcards plus 1–2 production exercises generated
by the LLM, graded by LLM + LanguageTool, with feedback and explanations, all feeding the event log.

## 1. LLM layer (`backend/app/llm/`, A§7)

### 1.1 Interface
- `client.py`: `LLMClient` Protocol with, in M2: `generate_exercise`, `grade_sentence`, `explain`.
  Errors: `LLMError` (base), `LLMRefusal` (final `stop_reason == "refusal"`), `LLMUnavailable`.
- `types.py`: Pydantic request/response models (§2.2, §3.2, §4). Response models are the structured
  output schemas: keep them simple (no unions of objects, no free-form dicts), all fields required
  or with defaults.
- `prompts/<task>.v<N>.md`: one file per prompt version, with two sections `## system` and `## user`;
  the user section is a `string.Template` (`$name` placeholders). The loader returns
  `(system, user_template, version)`. Prompts are written in English; they instruct the model to
  write learner-facing text in the learner's explanation language (Italian in v1).
- `llm_calls` table (migration `0003`): `id`, `ts`, `task`, `prompt_version`, `model`, `request` JSON
  (the full request minus the API key), `response` JSON (parsed output or raw text), `stop_reason`,
  `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `latency_ms`, `error` text
  null. Every call is logged, including failures.

### 1.2 `AnthropicLLMClient`
- Official `anthropic` Python SDK. Structured output via `messages.parse(..., output_format=<PydanticModel>)`
  → `response.parsed_output`.
- Per-task configuration in settings (`LLMLL_LLM_TASKS` JSON override), defaults:

  | Task | model | effort | max_tokens |
  |---|---|---|---|
  | `generate_exercise` | `claude-opus-5-5` | `medium` | 4000 |
  | `grade_sentence` | `claude-opus-5-5` | `high` | 4000 |
  | `explain` | `claude-opus-5-5` | `medium` | 3000 |

  Effort goes in `output_config={"effort": ...}`. Do not send `thinking` (the model default is adaptive
  and `disabled` is rejected), `temperature`, or assistant prefill.
- **Prompt caching:** `system` as a list with one text block carrying
  `cache_control={"type": "ephemeral"}`; stable per-item context (grammar reference text) as the first
  user content block, also with `cache_control`; the variable part (answer, exercise) last.
- **Refusals:** opt into server-side fallback (`betas=["server-side-fallback-2026-07-01"]`,
  `fallbacks="default"`) via the beta messages namespace if the installed SDK supports it together with
  structured output; otherwise call without it. Always check `stop_reason` before reading the output;
  a final `refusal` raises `LLMRefusal` (logged with `stop_details`).
- Errors: rely on SDK retries (`max_retries=2`); map `APIConnectionError`/`RateLimitError`/5xx to
  `LLMUnavailable`, other API errors to `LLMError`.
- Never log the API key; read it from settings (`ANTHROPIC_API_KEY`).

### 1.3 `FakeLLMClient`
Deterministic, no network. Used by tests, and at runtime when `LLMLL_LLM_PROVIDER=fake` or no API key
is configured (the health endpoint reports `llm: "fake" | "anthropic"`, and the UI shows a banner).
- `generate_exercise`: template-based exercise from the target items (e.g. translation of the item's
  curriculum example), reference solution = the example's German sentence.
- `grade_sentence`: normalized comparison with the reference solutions; mismatch → one `major` error
  on the first target item, confidence 0.9.
- `explain`: returns the first paragraph of the item's `reference_it`.

## 2. Production exercises

### 2.1 Session composition (replaces M1 §4.3 step 2, R§7.4, R§10)
`POST /api/sessions` now returns:
1. Due lemma flashcards (as in M1), up to `review_cap − production_slots`.
2. `production_slots` (setting, default 2) production exercises, created as `exercises` rows with
   `status = pending` and no prompt yet. Each slot gets **targets** chosen by a pure function
   `plan_production(...)` in `app/domain/production.py`:
   - priority 1: items in the remediation queue (§3.4);
   - priority 2: due grammar/construction memories (lowest retrievability first);
   - priority 3: new items from the candidate queue within the weekly budget: at most 1 new grammar
     point and up to 3 new lemmas per exercise;
   - every exercise has 1 primary target (grammar point or construction when available) and 0–3
     secondary targets (lemmas); weights 1.0 primary, 0.5 secondary, 0.3 new lemmas.
   - type: `translation` if there is a new grammar point or the primary is weak (mastery < 0.5),
     otherwise alternate `guided` / `transform` / `translation`.
3. New **grammar** points get a `grammar_intro` card placed before their exercise: title, the first
   section of `reference_it`, examples; answering it emits `introduce` (facet `production`).
   New **lemmas** are no longer introduced with `flashcard_intro`: they appear in the exercise glossary
   and are introduced when the exercise is answered. (`flashcard_intro` remains only as a fallback when
   LLM generation fails.)

Exercise schema additions (migration `0003`): `status` (`pending|ready|answered|failed`), `targets`
gains `new: bool`.

### 2.2 Generation (`generate_exercise`)
`POST /api/exercises/{id}/prepare` → idempotent: if `pending`, call the LLM and store the result; returns
the card. The frontend calls it for all production slots right after the session starts (prefetch),
so generation overlaps with the flashcards.

Request (`ExerciseRequest`): exercise type; level; explanation language; targets with their curriculum
data (lemma payloads, grammar title + `reference_it` + diagnostic tags, construction pattern); which
targets are new; a sample of known vocabulary (≤ 150 lemmas with status `introduced` or
`presumed_known`, highest mastery first, plus all lemmas at levels below the learner's level if fewer).

Response (`GeneratedExercise`):
`instructions` (learner language), `prompt` (Italian sentence(s) to translate, or a situation for
guided, or a German sentence to transform), `glossary: [{item_id, de, translation}]` (must include every
new lemma), `reference_solutions: [str]` (1–3 German answers), `targets: [{item_id, weight}]`.

Validation: unknown target ids are dropped; every requested new lemma must be in the glossary
(otherwise retry once, then mark `failed` and fall back to flashcards for those lemmas). Lemma-coverage
checks of the prompt need the NLP layer and arrive in M3.

### 2.3 Card payload for production exercises
`{exercise_id, type: "production", subtype, instructions, prompt, glossary, item_ids}`, never the
reference solutions.

## 3. Grading (A§6.2, R§8)

### 3.1 LanguageTool client (`app/nlp/languagetool.py`)
`check(text, language="de-DE") -> list[LTMatch]` against `{languagetool_url}/v2/check` (form-encoded,
`httpx`, timeout 5 s). `LTMatch`: `offset`, `length`, `rule_id`, `category`, `message`, `replacements`
(first 3). If the server is unreachable, return `None` (no signal) and log a warning; grading continues.

### 3.2 LLM grading (`grade_sentence`)
`POST /api/sessions/{sid}/answers` with `{exercise_id, answer: {text}, used_hint, duration_ms}` for a
production exercise runs: LanguageTool → LLM → reconciliation → evaluation → events.

Request (`GradeRequest`): exercise (type, instructions, prompt, glossary, reference solutions), learner
answer, targets with curriculum data and **allowed diagnostic tags**, LanguageTool matches, level,
explanation language. The prompt must state: accept any correct variant (reference solutions are
examples, not the only answer); stylistic preferences are not errors; report errors only with a
concrete correction; attribute each error to a curriculum item id from the provided list when
possible; report correct uses of target items.

Response (`GradeResult`):
- `overall`: `correct | minor_errors | major_errors | off_task`
- `errors: [{start, end, original, correction, item_id (nullable), diagnostic_tags, severity: minor|major,
  confidence (0–1), explanation (one sentence, learner language)}]` — `start/end` are character offsets
  in the learner answer
- `correct_uses: [item_id]`
- `corrected_sentence`
- `feedback` (2–3 sentences, learner language, encouraging, prioritizing target-item errors, R§8
  "don't correct everything")

### 3.3 Reconciliation (pure: `app/domain/reconcile.py`)
`reconcile(grade, lt_matches, targets, known_item_ids, allowed_tags, cfg) -> Evaluation`:
- drop `item_id`s not in the curriculum (keep the error, `item_id = null`) and tags not allowed for that
  item (record both drops in `notes`);
- per error: if an LT match overlaps its span → `confidence = max(conf, cfg.lt_agree_confidence)` (0.9);
  if `severity == major`, no overlapping LT match and `conf < 0.8` → `conf *= cfg.lt_disagree_factor` (0.8);
- LT matches overlapping no LLM error → `unmatched_lt` list; if non-empty, correct uses get confidence
  `cfg.unmatched_lt_confidence` (0.7) instead of 1.0;
- LT unavailable (`None`) → no adjustments, `lt_available = false`;
- per-item outcomes: for each target and each error/correct-use item that is known to the learner
  (`introduced`/`presumed_known`, or a target): any `major` error → `error`; only `minor` → `assisted`;
  otherwise in `correct_uses` or a target with no errors and `overall in {correct, minor_errors}` →
  `correct`; `off_task` → targets `error` with confidence 0.5 (uncertain);
  `used_hint` turns `correct` into `assisted`. Item confidence = min confidence of its errors, or the
  correct-use confidence.
- output `Evaluation`: per-item `{item_id, outcome, confidence, diagnostic_tags}`, the cleaned errors,
  `unmatched_lt`, `notes`, `reconcile_version`.

### 3.4 Persistence and effects
- `evaluations` table (migration `0003`): `id`, `attempt_id`, `llm_call_id`, `lt_matches` JSON, `result`
  JSON (reconciled `Evaluation` + `corrected_sentence` + `feedback`), `grader_version`
  (`prompt version | model | reconcile version`), `supersedes` null, `created_at`.
- Events: targets → `review` (weight from exercise type: `translation`, `guided`, `transform` →
  `guided` weight, R§4.2); non-target known items → `implicit` with `implicit_sentence` weight; new
  targets get their `introduce` event first. Events carry `confidence`, `diagnostic_tags`,
  `evaluation_id`.
- `GradeDecision.needs_remediation` → `remediation_queue` table: `item_id`, `diagnostic_tags`,
  `evaluation_id`, `created_at`, `consumed_at`; consumed when a production exercise targets it.
- The answer response for production exercises returns: `{outcome (overall), corrected_sentence,
  errors (with spans), feedback, items: [{item_id, label, outcome, needs_remediation}], evaluation_id}`.

## 4. Explanations (R§9)
- `explain` request: item (title, `reference_it`, diagnostic tags), optional error context (learner
  answer, error span, correction, tags), optional free question, learner level, explanation language,
  list of grammar points the learner has already met (status `introduced`/`presumed_known`) — the
  explanation must not rely on others. Response: `{markdown, examples: [{de, translation}]}`.
- Anchoring: the prompt includes `reference_it` and instructs to stay consistent with it and to say
  so if the question goes beyond it.
- Endpoints: `POST /api/evaluations/{id}/explain {item_id}` (error explanation, cached per
  evaluation+item in an `explanations` table) and `POST /api/grammar/{id}/explain {question}`
  (on-demand).
- The frontend requests the error explanation automatically when an item `needs_remediation`, and on
  demand ("Spiegami meglio") otherwise.

## 5. Frontend
- Production card: instructions, prompt, glossary (new words highlighted), multiline input with
  `ä ö ü ß Ä Ö Ü` buttons, `lang="de"`, autocorrect/autocapitalize off; "Check". Loading state while
  grading (can take several seconds).
- Feedback view: learner answer with error spans highlighted (tap an error → correction + one-line
  explanation), corrected sentence, feedback, per-item outcomes; explanation panel (Markdown) for
  remediation items or on "Spiegami meglio"; a disabled "Secondo me era giusto" button (enabled in M4).
- `grammar_intro` card.
- Grammar detail: "Fai una domanda" box → `POST /api/grammar/{id}/explain`.
- Banner when the backend runs with the fake LLM.
- All learner-facing UI strings for the learning flow stay in English for now except content produced
  by the backend (explanation language); UI i18n is out of scope.

## 6. CI
Add a step to the backend job: export the OpenAPI schema to a temp file and diff it against
`frontend/src/api/openapi.json`; and in the frontend job, regenerate `schema.d.ts` from the committed
`openapi.json` and `git diff --exit-code`.

## 7. Tests (must exist)
- Prompt loader; request building of `AnthropicLLMClient` with a mocked SDK client (model, effort,
  cache_control placement, fallback args, output schema), refusal → `LLMRefusal`, every call logged.
- `FakeLLMClient` behaviour.
- LanguageTool client with `httpx.MockTransport` (matches, unreachable → `None`).
- `reconcile`: every rule in §3.3 has a test.
- `plan_production`: priority order, budget respected, at most one new grammar point.
- API end to end with the fake LLM and a mocked LanguageTool: session with production slots → prepare →
  answer → evaluation, events (introduce + review + implicit), remediation queue, explanation endpoint;
  replay after the flow equals incremental state.
